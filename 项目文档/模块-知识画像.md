# 模块-知识画像

## 1. 职责与边界

### 模块职责

读取 `notes/` 中的笔记 markdown，调用 LLM 提炼其中的编程知识点，维护画像文件 `profile/knowledge.md`：每个知识点带状态（学过/做过/存疑）与证据（来自哪篇笔记或哪个产出）。

### 不负责什么

- 不生成练习任务（那是 [[模块-任务生成]] 的事）。
- 不修改 `notes/` 原始笔记。
- 不评估非编程内容（高数、英语等笔记提示「无可提炼编程知识点」后跳过）。

### 上下游关系

| 方向 | 模块/系统 | 交换内容 | 约定 |
| --- | --- | --- | --- |
| 输入 | 本地 `notes/` | 笔记 markdown | 由 [[模块-笔记同步]] 产出 |
| 输入 | LLM API | 笔记正文 + 提炼 prompt | 发送内容不含凭证 |
| 输出 | `profile/knowledge.md` | 画像文件 | 写入先临时后替换；可被客户手工编辑 |

## 2. 功能清单

| 编号 | 功能 | 输入 | 输出 | 关联需求/验收 |
| --- | --- | --- | --- | --- |
| M-01 | 提炼并合并知识点 | notes/*.md | 更新后的 knowledge.md | [[01-需求与范围确认#7. 验收标准]] A-02 |
| M-02 | 状态回写（done） | 知识点名 + 产出路径 | 状态「学过→做过」并附证据 | A-04 |

## 3. 核心流程

### 流程： 提炼一篇笔记

1. 读取画像现有内容（无则空）。
2. 把笔记正文 + 现有画像知识点名单发给 LLM，要求输出：新知识点、状态升级、存疑项。
3. 解析 LLM 输出，合并进画像（已存在的知识点不重复添加，只做状态升级/证据追加）。
4. 先写临时文件，成功解析并合并后才替换 `knowledge.md`；任何一步失败保留旧画像。

## 4. 数据与接口

### 数据结构

| 字段/对象 | 类型 | 含义 | 必填 | 来源 | 去向 |
| --- | --- | --- | --- | --- | --- |
| 知识点.name | string | 知识点名称 | 是 | LLM 提炼 | 画像 |
| 知识点.level | enum | 学过 / 做过 / 存疑 | 是 | LLM 或 done 命令 | 画像、[[模块-任务生成]] |
| 知识点.evidence | string | 证据（笔记文件名或产出路径） | 是 | 同步模块/客户 | 画像 |
| 知识点.topic | string | 归属主题（如 Python 基础） | 否 | LLM 提炼 | 画像 |

### 接口/事件

| 名称 | 调用方 | 输入 | 成功输出 | 失败输出 | 说明 |
| --- | --- | --- | --- | --- | --- |
| LLM 提炼调用 | 本模块 | 笔记文本+画像名单 | 结构化知识点列表 | 解析失败标记 | prompt 约束输出为可解析格式；失败不改动画像 |

## 5. 状态、错误与排查

| 状态/错误码 | 触发条件 | 用户可见结果 | 系统行为 | 优先排查位置 | 是否可重试 |
| --- | --- | --- | --- | --- | --- |
| LLM 接口失败 | 网络/额度错误 | 报错，提示画像未变 | 保留旧画像 | LLM 额度与网络 | 是 |
| LLM 输出不可解析 | 返回非约定格式 | 报错并提示重试 | 保留旧画像 | 提炼 prompt | 是 |
| 非编程笔记 | 无编程知识点 | 提示跳过 | 画像不变 | 笔记内容 | 否 |

> [!warning] 未知情况
> LLM 提炼结果与客户实际掌握程度不符时，以「存疑」状态落库，由客户手工改为「学过/做过」；不得把 LLM 的猜测当作已掌握事实。

## 7.1 提炼约定（T-003 实测确认）

### provider 与模型

Kimi 有**两个互不通用的平台**，端点与 Key 都不同（官方文档 www.kimi.com/code/docs/kimi-code/faq.html）：

`provider=kimi` 时按下面的优先级取凭证（T-011 实测确认）：

| 优先级 | 凭证来源 | base_url | 模型 | 环境变量 |
| --- | --- | --- | --- | --- |
| 1 | 显式 API Key（coding plan） | `https://api.kimi.com/coding/v1` | `kimi-for-coding` | `KIMI_API_KEY` |
| 2 | **Kimi Code CLI 登录态**（默认主路径） | `https://api.kimi.com/coding/v1` | `kimi-for-coding` | `~/.kimi-code/credentials/kimi-code.json` |
| 3 | 开放平台按量 Key | `https://api.moonshot.cn/v1` | `kimi-k2.7-code` | `MOONSHOT_API_KEY` |
| — | DeepSeek（备用 provider） | `https://api.deepseek.com/v1` | `deepseek-chat` | `DEEPSEEK_API_KEY` |

- **登录态是主路径**：`.env` 不配任何 Kimi Key 也能调用，凭证由 Kimi Code CLI 的 `/login` 维护。
- 登录态过期且没有任何 Key 时，报错提示「请重新登录：在 Kimi Code CLI 里执行 /login」；**不实现自动刷新**。
- 显式配了 `KIMI_API_KEY` 时以 Key 优先，不会悄悄改用登录态。
- `KIMI_MODEL` 可覆盖模型名；`KIMI_BASE_URL` 可覆盖端点（走代理/自建网关）。
- coding 端点的可用模型**与开放平台不同**：`GET /coding/v1/models` 实测返回 `kimi-for-coding` / `kimi-for-coding-highspeed` / `k3` / `k3-256k`。
- coding 模型**只接受 `temperature=1`**（传 0 会 HTTP 400 invalid temperature），因此请求默认不带 temperature；DeepSeek 仍带 0 以保持确定性。
- `moonshot-v1` 全系列已于 2026-08-31 下线，不得作为默认模型。

### prompt 与输出契约

- 输出契约：JSON 数组，元素含 `name`（必填）、`level`（必填，三态之一）、`evidence`（必填）、`topic`（可选）。
- `level` 判定口径：做过 = 看得出动手写过代码/有产出；学过 = 有清晰解释或示例但看不出动手；存疑 = 只提一句、理解不完整、或无法确定是否掌握。
- prompt 明确禁止臆断已掌握，拿不准一律「存疑」。实测：只有一句描述、无示例的知识点被判「存疑」。
- LLM 只给小节标题（或证据为空）时，回笔记取该小节正文作为证据；取不到则报错，不写入空证据。
- 解析前先剥离 markdown 代码围栏（模型常把 JSON 放在 ```json 里）；失败时报可操作的原因，画像保持不变。

## 7.2 画像文件结构与合并规则（T-004 实现）

### 文件结构（profile/knowledge.md）

```markdown
---
title: 知识画像
tags:
  - profile
---

# 知识画像

## 统计

| 状态 | 数量 |
| --- | --- |
| 学过 | N |
| 做过 | N |
| 存疑 | N |

## <主题>

- [状态] 知识点名称（主题） — 证据：...
```

- 一行一个知识点；解析正则只认「`- [三态之一] 名称 — 证据：...`」，**不认识的行一律忽略，绝不猜**。
- 无主题的知识点归入「未分类」；主题来自 `## <主题>` 小节。
- 渲染往返稳定：`render(parse(render(x))) == render(x)`。

### 合并规则（merge_points）

| 规则 | 说明 |
| --- | --- |
| 身份 | **按知识点名称判定**（不把主题算进身份） |
| 主题 | 既有点的主题优先保留；既有无主题才用新点的主题补 |
| 状态 | 只升不降（存疑 < 学过 < 做过）；**唯一例外**：新点为「存疑」时允许下降，作为「信息不足、请复核」的信号 |
| 证据 | 新证据不是旧证据子串时追加（`；` 分隔），重复不追加 |
| 落盘 | 先写 `knowledge.md.tmp` 再替换；渲染或写入失败都保留旧画像，不残留临时文件 |

> [!warning] 为什么身份按名称而不是「名称+主题」
> 实测同一篇笔记重复提炼时，LLM 给同一知识点的主题会漂移（同一个「Markdown」一次「工具使用」、一次「工具」）。
> 若把主题算进身份，每跑一次提炼画像就会多一条重复项，最终被撑爆。已用回归测试锁住。

### 回写规则（mark_done，T-006）

| 项 | 规则 |
| --- | --- |
| 定位 | 按**归一化名称**匹配（去掉结尾「（主题）」），例：`done 列表（Python 基础）` 也能命中「列表」 |
| 状态 | 一律置「做过」（从「学过」或「存疑」都可以升） |
| 证据 | 追加 `产出：<路径>`，保留原证据；重复 done 同一路径不重复追加（幂等） |
| 其他知识点 | 不动（有测试锁定） |
| 找不到 | 报错并列出可选知识点，画像字节不变 |
| 落盘 | 复用 write_profile_atomic（临时文件 + 替换） |

### 批量提炼（T-016）

| 项 | 约定 |
| --- | --- |
| 入口 | 命令行 `distill --all`；看板「提炼知识点」按钮（内部走同一个 `--all`） |
| 输入范围 | `notes/` 下全部 **非空** `.md`，按文件名排序（结果稳定可复现） |
| 逐篇行为 | 单篇失败（LLM 报错 / 输出不可解析 / 读取失败）**只记进失败清单，不阻塞其余篇目** |
| 汇总 | 逐篇汇报成败：`[成功] a.md：N 个知识点` / `[失败] b.md：原因`；结尾给合计 |
| 退出码 | 全部成功 → 0；**有失败篇目 → 1**（但成功的篇目照常写入画像，不整批回滚） |
| 幂等 | 重复跑不新增重复条目（依赖 T-004 的「按名称合并」）；实测两次跑条数不变 |
| 增量（T-017 I-2） | 按**内容 sha256 指纹**比对 `profile/.distill-state.json`，未变更的笔记直接跳过不调 LLM；`--force` 可强制全部重跑 |
| 状态文件更新时机 | **只有成功篇目写入状态**；失败篇目不写，下次自动重试（所以"重跑"天然会补上失败的） |
| 进度提示（T-017 I-1） | 每篇回调/打印 `[i/n] 文件名 — 提炼中 / 成功（N 个知识点） / 跳过（内容未变） / 失败`，带 flush 不缓冲 |
| 无笔记 | `notes/` 没有非空笔记 → 退 0 并提示，不算错误 |
| 落盘 | 汇总后一次性合并 + 原子替换（`write_profile_atomic`）；写入失败则画像不动 |

> [!note] 为什么不是"一篇一篇调 distill"
> 原先 CLI 一次只收一个文件、看板只挑 mtime 最新的一篇，导致画像只覆盖到最新那篇笔记。
> 批量入口让"同步完 → 一次提炼全部"成为一条命令，也让看板按钮名副其实。

### 手工改状态（set_level，T-013）

| 项 | 规则 |
| --- | --- |
| 入参 | `name` + `level` + 可选 `note`（`note` 用于复核说明/复述；看板表单里另有 `recite` 与 `path`） |
| level | 必须是三态白名单之一（学过/做过/存疑），否则报错**不写文件** |
| note | 非空时追加进证据（产出路径或复核说明），沿用「不重复追加」规则 |
| 范围 | 只改目标知识点，其他知识点与顺序不动 |
| 定位 | **精确同名优先**；其次按归一化名称匹配且**必须唯一**；多条候选 → 报歧义并列出（名称+主题）让客户端带完整名称重试；零条 → 报错并列出全部候选（T-014） |
| 落盘 | 复用 write_profile_atomic（临时文件 + 替换） |
| 调用方 | 看板状态表单（T-013）；参数非法时页面显示可读原因，画像字节不变 |

### 四态与「输出」（T-019 / F-08）

状态机从三态扩展为四态，掌握程度严格递增：

| 状态 | 含义 | rank |
| --- | --- | --- |
| 存疑 | 笔记里只提到，没解释/没示例；**不计入已掌握** | 0 |
| 学过 | 有解释或示例，看过 | 1 |
| 做过 | 自己动手做出过东西（`done` 的最小结果） | 2 |
| **输出** | **能用自己的话讲清楚**（费曼复述） | 3 |

- `done <知识点> <产出> --recite "<复述>"`：带复述时升到「输出」，复述文字进证据；
- 看板状态表单可选「输出」，并有独立「费曼复述」输入框（提交后走同一个 `mark_done`）；
- 看板「回写」表单是完整三件套（知识点下拉 / 产出路径 / 可选复述）——**T-024 M-01**：原先是个裸按钮，点下去必失败；
- 下拉候选取自 `tasks.md` **最近一次任务**涉及的点（含新点），读不到退化为文本输入；
- **done 只升不降**：记录产出不该把状态改低。实测曾出现「输出」被普通 done 降回「做过」，已修；
- `set_level`（手工改状态）**允许下调** —— 那是明确的手工意图，与 done 的语义不同；
- 看板配色四态各一色：学过蓝 / 做过绿 / **输出紫** / 存疑橙。

> [!important] 画像里没有的知识点会**新增**，不是报错（T-023 L-01）
> 早期实现里 `done` / 看板改状态遇到画像里没有的点会直接报错，导致**核心闭环断裂**：
> 出题与讲解里遇到的新知识点，做完根本没法回写。
> 现在 `mark_done` 与 `set_level` 都会**新增条目**（状态分别为「做过」/「输出」/所选状态，主题为空=未分类）。
> **例外**：归一化后与既有条目撞名（同名不同主题）时**仍然报错**并列出候选——
> 那需要人工判断改哪一条，不该自动新建（T-014 的规则不受影响）。

> [!warning] 名称里的括号必须有「保真」保证（T-010 实测修复）
> 渲染写法是 `- [状态] 名称（主题） — 证据：…`。若**名称本身以括号结尾**，
> 解析时无法区分结尾括号是「主题」还是名称的一部分。
> 旧实现无条件剥掉结尾括号 → 实测 `列表（ul/ol/li）` 被读成 `列表`（与另一条撞名），
> 画像**每次读写都静默失真**，题库标签也全部匹配不上。
> 现在的规则：**只有当结尾括号的内容等于本节主题时才剥掉它**（`_split_point(rest, topic)`）。
> 另有 `_TOPIC_SUFFIX_RE` 曾被重复定义两次的隐患，已删除重复。

> [!warning] 为什么定位要「精确优先 + 歧义报错」（T-014 实测）
> 归一化会去掉结尾的「（主题）」，于是**不同主题的同名条目会撞名**。客户真实画像里就同时存在
> 「列表（ul/ol/li）」（HTML 基础）与「列表」（Python 基础）。
> 早期实现取「第一个归一化命中」，导致改「列表」时误改 HTML 那条**还报成功**。
> 现在：精确同名优先；归一化命中多条一律报歧义（列出候选与主题），**绝不模糊命中后报成功**。
> set_level 与 mark_done 共用同一解析器。

> [!note] 已知限制
> 画像**只增不删**：某次提炼若冒出笔记里并不存在的新名称，该条目会被保留（合并逻辑刻意不删，以免误删客户手工维护的条目）。
> 根治要靠在提炼 prompt 侧收紧（属 T-003 的后续迭代），不在本模块。
